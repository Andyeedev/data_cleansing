## 1. Overview

This document defines the metrics framework for measuring AI-assisted development effectiveness across the MAP platform. Metrics are organized into five categories covering productivity, quality, documentation, prompt effectiveness, and developer experience.

---

## 2. Productivity Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Time saved per feature | 40% | Manual time vs AI-assisted time |
| Code generation rate | 30% | Lines of code generated by AI |
| Boilerplate reduction | 60% | Reduction in repetitive code |

### 2.1 Time Saved Per Feature

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage reduction in development time when using AI tools compared to manual development |
| **Target** | 40% reduction |
| **Measurement** | Track time in Azure DevOps work items for AI-assisted vs non-AI-assisted features |
| **Frequency** | Per sprint (bi-weekly) |
| **Data Source** | Azure DevOps, developer time tracking |
| **Owner** | Engineering Manager |

**Calculation:**
```
Time Saved % = ((Manual Time - AI-Assisted Time) / Manual Time) * 100
```

**Measurement Process:**
1. Baseline: Track manual development time for 2 sprints before AI adoption
2. Comparison: Track equivalent feature development time with AI tools
3. Aggregation: Calculate average time savings across all features
4. Reporting: Report per sprint with rolling 30-day average

### 2.2 Code Generation Rate

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of total code lines generated by AI tools (Copilot, Cursor, etc.) |
| **Target** | 30% of total lines |
| **Measurement** | Git blame analysis with AI tool attribution |
| **Frequency** | Weekly |
| **Data Source** | Git repository, AI tool telemetry |
| **Owner** | Tech Lead |

**Calculation:**
```
Code Generation Rate = (AI-Generated Lines / Total Lines Committed) * 100
```

**Measurement Process:**
1. Tag commits with AI tool usage flag
2. Use git blame to attribute lines to AI vs manual
3. Exclude auto-generated files (migrations, protobuf, etc.)
4. Report weekly by team and project

### 2.3 Boilerplate Reduction

| Attribute | Value |
|-----------|-------|
| **Definition** | Reduction in repetitive code patterns through AI-assisted generation |
| **Target** | 60% reduction |
| **Measurement** | Count of boilerplate patterns before and after AI adoption |
| **Frequency** | Monthly |
| **Data Source** | Static analysis tools, code review logs |
| **Owner** | Tech Lead |

**Calculation:**
```
Boilerplate Reduction % = ((Pre-AI Boilerplate Count - Post-AI Boilerplate Count) / Pre-AI Boilerplate Count) * 100
```

**Boilerplate Indicators:**
- DTO classes with only property definitions
- Repository pattern implementations
- Unit test scaffolding
- API endpoint boilerplate
- Configuration classes

## 3. Quality Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Defect rate | 50% reduction | Bugs per feature |
| Code review pass rate | 90%+ | First-time approval rate |
| Test coverage | 80%+ | Automated coverage measurement |

### 3.1 Defect Rate

| Attribute | Value |
|-----------|-------|
| **Definition** | Number of defects discovered per feature, comparing AI-assisted vs manual development |
| **Target** | 50% reduction |
| **Measurement** | Bugs tracked in Azure DevOps per work item |
| **Frequency** | Per release |
| **Data Source** | Azure DevOps bug tracking |
| **Owner** | QA Lead |

**Calculation:**
```
Defect Rate = Total Bugs / Total Features Released
Defect Reduction % = ((Pre-AI Rate - Post-AI Rate) / Pre-AI Rate) * 100
```

**Measurement Process:**
1. Tag bugs with AI-assisted development flag
2. Track defect discovery phase (dev, QA, production)
3. Calculate defect density per feature
4. Report per release with severity breakdown

### 3.2 Code Review Pass Rate

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of pull requests approved on first review without changes |
| **Target** | 90%+ first-time approval |
| **Measurement** | Pull request approval tracking in Azure DevOps |
| **Frequency** | Weekly |
| **Data Source** | Azure DevOps pull request analytics |
| **Owner** | Tech Lead |

**Calculation:**
```
Pass Rate = (PRs Approved First Time / Total PRs) * 100
```

**Measurement Process:**
1. Track PR creation and approval events
2. Identify PRs requiring 0 review rounds
3. Compare AI-generated code vs manual code pass rates
4. Report weekly by team

### 3.3 Test Coverage

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of code covered by automated tests |
| **Target** | 80%+ coverage |
| **Measurement** | Coverlet for .NET, pytest-cov for Python |
| **Frequency** | Per build |
| **Data Source** | CI/CD pipeline coverage reports |
| **Owner** | QA Lead |

**Calculation:**
```
Coverage % = (Covered Lines / Total Lines) * 100
```

**Measurement Process:**
1. Generate coverage report in CI/CD pipeline
2. Track coverage per project and module
3. Compare AI-generated test coverage vs manual test coverage
4. Enforce minimum coverage threshold in pipeline

## 4. Documentation Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Documentation coverage | 95%+ | Public APIs documented |
| Documentation accuracy | 90%+ | Manual verification |
| README completeness | 100% | All projects have README |

### 4.1 Documentation Coverage

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of public APIs with complete documentation |
| **Target** | 95%+ coverage |
| **Measurement** | OpenAPI spec coverage analysis |
| **Frequency** | Weekly |
| **Data Source** | Swagger/OpenAPI spec, XML documentation |
| **Owner** | Documentation Lead |

**Calculation:**
```
Documentation Coverage % = (Documented APIs / Total Public APIs) * 100
```

**Measurement Process:**
1. Parse OpenAPI spec for documented endpoints
2. Compare against actual API endpoints in codebase
3. Identify undocumented parameters and responses
4. Report weekly with gap analysis

### 4.2 Documentation Accuracy

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of documentation that accurately reflects current implementation |
| **Target** | 90%+ accuracy |
| **Measurement** | Manual verification + automated link checking |
| **Frequency** | Monthly |
| **Data Source** | Documentation review logs, broken link reports |
| **Owner** | Documentation Lead |

**Calculation:**
```
Accuracy % = (Verified Accurate Items / Total Documentation Items) * 100
```

**Measurement Process:**
1. Monthly documentation audit by team members
2. Automated link checking in CI/CD pipeline
3. API response validation against documented schemas
4. Report with accuracy breakdown by section

### 4.3 README Completeness

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of projects/modules with complete README files |
| **Target** | 100% coverage |
| **Measurement** | Automated README presence and section checking |
| **Frequency** | Weekly |
| **Data Source** | Repository analysis script |
| **Owner** | Documentation Lead |

**Calculation:**
```
Completeness % = (Projects with Complete README / Total Projects) * 100
```

**README Checklist:**
- [ ] Project description
- [ ] Prerequisites
- [ ] Setup instructions
- [ ] Configuration
- [ ] Usage examples
- [ ] Testing instructions
- [ ] Deployment guide
- [ ] Contributing guidelines

## 5. Prompt Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Prompt reuse rate | 60%+ | Prompts used more than once |
| Prompt accuracy | 85%+ | Valid outputs / total outputs |
| Prompt library size | Growing | Number of prompts |

### 5.1 Prompt Reuse Rate

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of prompts in the library that have been used more than once |
| **Target** | 60%+ reuse rate |
| **Measurement** | Prompt usage tracking in development workflow |
| **Frequency** | Monthly |
| **Data Source** | Prompt library usage logs |
| **Owner** | AI Engineering Lead |

**Calculation:**
```
Reuse Rate % = (Prompts Used >1 Time / Total Prompts Used) * 100
```

**Measurement Process:**
1. Log prompt usage with timestamp and user
2. Count unique prompt invocations per prompt ID
3. Calculate percentage of prompts with multiple uses
4. Report monthly with usage trends

### 5.2 Prompt Accuracy

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of prompt outputs that are valid and usable without major modifications |
| **Target** | 85%+ accuracy |
| **Measurement** | Developer feedback on prompt outputs |
| **Frequency** | Monthly |
| **Data Source** | Prompt usage feedback system |
| **Owner** | AI Engineering Lead |

**Calculation:**
```
Accuracy % = (Valid Outputs / Total Outputs) * 100
```

**Feedback Categories:**
- **Valid:** Output usable as-is or with minor formatting
- **Minor Fix:** Output requires minor edits (< 10% change)
- **Major Fix:** Output requires significant modifications (> 10% change)
- **Invalid:** Output not usable, must be regenerated manually

### 5.3 Prompt Library Size

| Attribute | Value |
|-----------|-------|
| **Definition** | Total number of prompts in the library, categorized by type |
| **Target** | Continuously growing |
| **Measurement** | Prompt library manifest count |
| **Frequency** | Monthly |
| **Data Source** | Prompt library manifest |
| **Owner** | AI Engineering Lead |

**Tracking:**
- Total prompt count
- Prompts per category
- New prompts added per month
- Deprecated prompts per month

## 6. Developer Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Developer satisfaction | 80%+ | Quarterly survey |
| AI tool adoption | 90%+ | Active users / total developers |
| Training completion | 100% | Completed AI training |

### 6.1 Developer Satisfaction

| Attribute | Value |
|-----------|-------|
| **Definition** | Developer satisfaction score with AI tools and workflows |
| **Target** | 80%+ satisfaction |
| **Measurement** | Quarterly anonymous survey |
| **Frequency** | Quarterly |
| **Data Source** | Developer experience survey |
| **Owner** | Engineering Manager |

**Survey Dimensions:**
1. Overall satisfaction with AI tools (1-10)
2. Productivity improvement perception (1-10)
3. Code quality impact perception (1-10)
4. Learning curve difficulty (1-5, lower is easier)
5. Tool reliability perception (1-10)
6. Open-ended feedback on improvements

**Scoring:**
```
Satisfaction Score = Average of all Likert-scale responses
Target: 8.0+ out of 10
```

### 6.2 AI Tool Adoption

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of developers actively using AI tools in their workflow |
| **Target** | 90%+ adoption |
| **Measurement** | AI tool telemetry and license usage |
| **Frequency** | Weekly |
| **Data Source** | GitHub Copilot dashboard, AI tool analytics |
| **Owner** | Engineering Manager |

**Calculation:**
```
Adoption Rate % = (Active AI Tool Users / Total Developers) * 100
```

**Active User Definition:**
- Minimum 10 AI-assisted commits per week
- OR minimum 5 Copilot suggestions accepted per day
- OR documented AI tool usage in sprint activities

### 6.3 Training Completion

| Attribute | Value |
|-----------|-------|
| **Definition** | Percentage of developers who have completed AI tool training program |
| **Target** | 100% completion |
| **Measurement** | Training platform completion records |
| **Frequency** | Monthly |
| **Data Source** | Learning Management System (LMS) |
| **Owner** | Engineering Manager |

**Training Modules:**
1. AI Tool Fundamentals (2 hours)
2. Prompt Engineering Best Practices (3 hours)
3. Code Review with AI (1 hour)
4. Security Considerations (1 hour)
5. Advanced Workflows (2 hours)

**Tracking:**
- Module completion per developer
- Overall completion percentage
- Time to complete training
- Assessment scores

## 7. Metrics Collection and Reporting

### 7.1 Data Collection

| Source | Data Collected | Frequency |
|--------|----------------|-----------|
| Azure DevOps | Work item time, PR analytics, bugs | Real-time |
| Git Repositories | Commit data, blame analysis | Daily |
| AI Tools | Usage telemetry, suggestion acceptance | Real-time |
| CI/CD Pipelines | Build results, coverage reports | Per build |
| Survey Platform | Developer satisfaction data | Quarterly |
| LMS | Training completion data | Monthly |
| Prompt Library | Usage logs, feedback | Real-time |

### 7.2 Reporting Cadence

| Report | Audience | Frequency | Format |
|--------|----------|-----------|--------|
| Sprint Metrics | Engineering Team | Bi-weekly | Dashboard |
| Monthly Metrics Report | Engineering Leadership | Monthly | PDF Report |
| Quarterly Business Review | Executive Team | Quarterly | Presentation |
| Real-time Dashboard | All Engineers | Continuous | Web Dashboard |

### 7.3 Dashboards

**Primary Dashboard (Grafana/Azure Dashboard):**
- Productivity metrics (time saved, code generation, boilerplate reduction)
- Quality metrics (defect rate, review pass rate, coverage)
- Real-time adoption and usage metrics

**Secondary Dashboard (Azure DevOps):**
- Work item completion trends
- PR cycle time metrics
- Build success rates

### 7.4 Alerting

| Metric | Threshold | Alert |
|--------|-----------|-------|
| Defect rate increase | > 20% from baseline | Engineering Manager notification |
| Test coverage drop | < 80% threshold | Build failure |
| Prompt accuracy drop | < 75% threshold | AI Engineering Lead review |
| Developer satisfaction drop | < 7.0 score | Quarterly review agenda item |

## 9. Continuous Improvement

### 9.1 Metrics Review

- Monthly review of all metrics with engineering leadership
- Quarterly calibration of targets based on actual performance
- Annual benchmark update against industry standards

### 9.2 Action Triggers

| Condition | Action |
|-----------|--------|
| Metric consistently below target for 2 sprints | Root cause analysis and improvement plan |
| Metric significantly exceeds target | Update target and document best practices |
| New AI tool or capability introduced | Add new metrics and adjust existing targets |
| Team structure changes | Recalibrate team-level metrics |

### 9.3 Success Criteria

The AI development initiative is considered successful when:
1. All productivity metrics meet or exceed targets
2. Quality metrics show no degradation
3. Developer satisfaction is 80%+
4. ROI positive within 6 months
5. Prompt library is actively maintained and growing
